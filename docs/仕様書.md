# Disk Ledger 仕様書

2026-11-14 時点。アプリ名は Disk Ledger。

## 1. 目的と範囲

システム設定で「システムデータ」とひとまとめにされ、中身が分からない容量を種類ごとに分けて見せ、それぞれが要るかどうかを判断できるようにする。図による見せ方は目的にしない（2026-11-14 に円形の図をやめた）。メモリ解放、マルウェア検査、アプリの最適化のような機能は作らない。

消す操作は最小限にとどめ、ゴミ箱へ移すことだけを許す。完全削除はアプリからは行わない。

この Mac の現状（2026-11-14、df）は、データ領域が使用 276GB、約240万項目、ローカルスナップショットが2本ある。最初の版はこの規模を数十秒で読み切ることを目標にする。

## 2. 構成

- SwiftUI のウィンドウアプリ。解析部は SwiftPM のライブラリ LedgerCore に分け、Time Machine Viewer の TMCore と同じ形にする
- Swift 6、配置対象は macOS 26.0（GitHub Actions の macos-latest で動かすため。Comma Switcher で 27.0 にして CI が落ちた経緯がある）
- サンドボックスは使わない。ホーム以外やライブラリの奥を読むためで、App Store には出さない。署名は当面ローカル署名、Hardened Runtime は有効にしておき、後から Developer ID と公証を足せるようにする
- 最初の画面でフルディスクアクセスを求め、許可されるまで走査を始めない。許可の有無は TCC のデータベースを開けるかで確かめる
- 許可がないまま読むと、デスクトップや他アプリのコンテナなどを開くたびに許可を求める窓が出る（2026-11-14、試しの走査で多数出た）。許可が効いていない場合に備え、許可がないときはそれらの場所に入らず「許可が必要」として残す
- ローカル署名ではビルドのたびに署名が変わり、許可が外れる。開発中は作り直すたびに許可し直す

## 3. 容量の数え方

ここが CleanMyMac 型アプリの正確さを左右するので、最初に決めておく。

| 項目 | 方針 |
|---|---|
| ファイルの大きさ | 論理サイズではなくディスク上の割り当てサイズ（totalFileAllocatedSize）で数える。疎なファイルや圧縮ファイルで差が出る |
| ハードリンク | inode 番号で一度だけ数える |
| APFS のクローン | 複製したファイルはブロックを共有しており、単純に足すと実際より大きくなる。getattrlistbulk の ATTR_CMNEXT_PRIVATESIZE で「消せば空く量」が取れる見込みなので、実機で確かめてから使う |
| iCloud の未ダウンロード | 中身がないファイルは 0 として数え、雲の印で区別する。走査がダウンロードを起こさないよう、中身は一切開かない。CloudStorage 配下は Time Machine の調査で走査が時間切れになった場所なので、既定では深く潜らず一覧だけ出す |
| ボリュームの境界 | 外部ディスクやネットワーク共有には入らない。/System/Volumes/Data の firmlink で同じものを二度数えない |
| パージ可能な領域 | volumeAvailableCapacityForImportantUsage と volumeAvailableCapacity の差を「macOS が必要に応じて空ける領域」として別に出す |
| ローカルスナップショット | tmutil listlocalsnapshots で本数を出す。スナップショットが残っている間は、ファイルをゴミ箱に入れて空にしても容量が戻らないことを、削除の前に知らせる |
| 説明のつかない分 | ボリュームの使用量から走査で数えた合計を引いた残りを「システムとその他」として一つの塊で出し、内訳があいまいなことを i ボタンで説明する |

## 4. 走査

- 列挙は FileManager の enumerator ではなく getattrlistbulk（または fts）で行う。一回の呼び出しでディレクトリ内の名前、種類、サイズ、inode をまとめて取れるため、数倍速い
- ホーム直下や /Applications などの上位のディレクトリごとに並列に走らせ、同時に動かす数は CPU の数程度に抑える
- 進み具合は、読んだ件数、読んだ容量、いま読んでいるパスで出す。分類は読み終えてから行う
- 結果の木は、ノード一つを数十バイトの構造体にして配列で持ち、名前は一つの文字列領域にまとめる。300万件でも 100MB 程度に収める
- 走査結果を Application Support に保存し、次に開いたときはすぐ前回の結果を出す。開いている間は FSEvents で変わったディレクトリだけを読み直す（第二段階）

## 5. 画面

- 左の一覧に、システムデータの種類を容量の大きい順に並べる。各行に容量と判断の目安を出し、見出しにシステムデータの合計を出す。最後に「フォルダで見る」を置き、ディスク全体を根から開いていけるようにする
- 右には選んだ種類に当たるフォルダを、容量の大きい順に表で並べる。名前の下に、どのアプリのものか（バンドル ID から引く）と、どこにあるかを小さく出す。行を開くとその中身に入り、見出しの道筋で戻れる
- 種類の見出しに判断の目安を出し、i ボタンの吹き出しで、それが何で、消すとどうなるかを説明する
- 項目の右クリックで Finder に表示、パスのコピーを出す（ゴミ箱に入れるは 0.3）
- 見ればわかる説明は書かない
- 書体はシステム標準（SF と ヒラギノ）で、Arial は使わない

### 見た目の方針（2026-11-14、参考画像なし）

モダンでありつつ堅実で、信頼感のある見た目にする。容量の数字を正しく読ませることを飾りより優先する。

- 骨組みは macOS 標準の部品だけで組む。サイドバーは NavigationSplitView、一覧は Table、ツールバーとシートも標準のものを使い、Liquid Glass はシステムが付ける分だけにとどめ、独自のガラスや光の効果は足さない
- 色は無彩色の地に、操作と強調だけに使う一色（落ち着いた紺青、ダークモードでは明るめ）を置く。判断の目安の文字だけ、作り直されるものを緑、消すと戻せないものを黄土にする。グラデーション、影の重ね、派手な警告色は使わない。赤はゴミ箱へ移す確認の画面だけに使う
- 数字は等幅の数字（monospacedDigit）で右にそろえ、単位は GB と MB を十進（1GB = 10億バイト）で Finder と合わせる。割合の棒は細く、角の丸みは小さくする
- 動きは控えめにする。走査中は件数と容量が増えていく表示にする
- ライトとダークの両方に対応し、システムのアクセントカラーと文字の大きさの設定に従う

## 6. システムデータの種類

Apple は「システムデータ」の定義を公開していないので、近い範囲を次のように決める。数えるのは ~/Library、ホームの . で始まるフォルダ、/Library、/private、データボリューム上の /System、/usr、/opt と、ファイルとして数えられなかった分。メール、メッセージ、iCloud Drive、ゴミ箱、アプリ、書類、macOS 本体はシステム設定でも別に出るので数えない。

種類は場所の決まり（LedgerCore の Categories.swift）で分ける。深い場所に当たる決まりを優先し、たとえばアプリの補助データの中の Code Cache はキャッシュとして数え、補助データからは引く。

| 種類 | 主な場所 | 判断の目安 |
|---|---|---|
| キャッシュ | ~/Library/Caches、/Library/Caches、Application Support の中の Cache や Code Cache | 消しても作り直される |
| ログと診断の記録 | ~/Library/Logs、/private/var/log、/private/var/db/diagnostics | 消しても作り直される |
| 一時ファイル | /private/var/folders、/private/tmp | macOS が管理 |
| 仮想メモリとスリープイメージ | /private/var/vm | macOS が管理 |
| macOS の追加データ | データボリューム上の /System（Apple Intelligence のモデル、辞書など） | macOS が管理 |
| macOS のアップデート | /Library/Updates | macOS が管理 |
| 検索の索引 | .Spotlight-V100 | 消しても作り直される |
| Xcode のビルドと端末のサポート | DerivedData、各 DeviceSupport | 消しても作り直される |
| シミュレータ | CoreSimulator | 再ダウンロードが必要 |
| 開発ツールのキャッシュ | ~/.npm、~/.cache、~/.gradle、~/.cargo/registry など | 消しても作り直される |
| 開発ツール | Homebrew、Command Line Tools、~/.rustup など | 入れ直せる |
| ローカル AI のモデル | ~/.lmstudio、~/.ollama、Hugging Face のキャッシュ | 再ダウンロードが必要 |
| 仮想マシンのディスク | Docker、Claude の vm_bundles、UTM | アプリのデータ |
| iPhone と iPad のバックアップ | MobileSync/Backup | 消すと戻せない |
| 音源とプラグイン | ~/Library/Audio、/Library/Audio | 再ダウンロードが必要 |
| アプリの補助データ | Application Support、Containers、Group Containers、Preferences など | アプリのデータ |
| スナップショットと読めない場所 | ボリュームの使用量から数えた分を引いた残り | macOS が管理 |
| 分類できなかったデータ | 範囲内でどれにも当たらなかった場所 | 中身を見て判断 |

「消してよい」とは断定せず、性質だけを示す。一括で掃除するボタンは作らない。

## 7. 大きいファイルと古いファイル

別のタブで、指定したサイズ以上のファイルを大きい順に並べ、種類と最終使用日で絞り込めるようにする。最終使用日はアクセス時刻があてにならないので、Spotlight の kMDItemLastUsedDate を使い、取れないものは更新日で代える。

## 8. ゴミ箱へ移す操作

- FileManager.trashItem だけを使い、rm 相当の処理はコードに持たない
- /System、/Library の Apple 管理部分、アプリ本体の中身、ホームの直下のフォルダそのものは選べないようにする
- 確認の画面に、選んだ件数と、クローンやハードリンクを考慮した実際に空く見込みの量を出し、ローカルスナップショットがある場合はその旨を添える
- 移した記録をアプリ内に残し、そこから元に戻すを呼べるようにする
